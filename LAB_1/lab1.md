Развернуть и настроить высокодоступный кластер PostgreSQL с использованием Patroni, Zookeeper и HAProxy. Проверить механизмы репликации, автоматического переключения при отказе (failover) и восстановления узлов.

## 4 Выполнение основного задания (Failover Test)

В соответствии с заданием было проведено тестирование отказоустойчивости путем принудительного отключения текущей мастер-ноды.

### Шаг 1. Принудительная остановка мастера

После перезапуска проекта в Части 3 роли были распределены заново: лидером стал контейнер `pg-slave` (`postgresql1`), а `pg-master` (`postgresql0`) перешел в роль реплики. Лидер выбирается через Zookeeper и не привязан к имени контейнера. Текущий лидер `pg-slave` был остановлен командой:

```bash
docker stop pg-slave
```

### Шаг 2. Автоматическое переключение (Failover)

После остановки лидера Patroni на оставшемся узле (`pg-master`) обнаружил потерю блокировки в Zookeeper и автоматически повысил себя до роли лидера.

> ![Логи pg-master после failover](img/06-failover-leader.png)

*Рисунок 6 − Логи `pg-master` после failover*

### Шаг 3. Проверка работоспособности через HAProxy

Несмотря на отказ основной ноды, подключение через HAProxy (порт 5432) осталось доступным. Была выполнена запись новых данных, что подтверждает успешную работу нового мастера.

> ![Данные после failover](img/07-data-after-failover.png)

*Рисунок 7 − Результат запроса `SELECT * FROM lab_test;` через порт 5432 после failover*

### Объяснение произошедшего

После остановки лидера Patroni на этом узле перестал обновлять ключ лидера в Zookeeper. По истечении ttl (30 с) блокировка была потеряна, и оставшийся узел, обнаружив отсутствие лидера, повысил себя до роли лидера.

HAProxy проверяет состояние узлов через REST API Patroni (порт 8008): код 200 возвращает только лидер. Остановленный узел не отвечал, поэтому после трех неудачных проверок (`fall 3`, интервал 3 с) был помечен как DOWN, а новый лидер получил статус UP. Существующие сессии были закрыты (`shutdown-sessions`), поэтому клиенту потребовалось переподключиться. Время недоступности определяется по меткам времени в логах.

### Шаг 4. Восстановление кластера (Auto-Recovery)

Остановленный узел был запущен повторно:

```bash
docker start pg-slave
```

После запуска узел автоматически определил текущего лидера и присоединился к кластеру в качестве реплики, начав синхронизацию недостающих данных.

## 5 Ответы на теоретические вопросы

### 5.1. Порты 8008 и 5432 вынесены в разные директивы, expose и ports. По сути, если записать 8008 в ports, то он тоже станет exposed. В чем разница?

Директива `ports` публикует порт на хост-машине. Docker пробрасывает порт хоста в контейнер, создавая маппинг между ними. Благодаря этому можно подключиться к контейнеру pg-master с хоста как `localhost:5433`, а к контейнеру pg-slave как `localhost:5434`. Эти порты доступны извне, в том числе из браузера или psql клиента на локальной машине.

Директива `expose` не экспортирует порт наружу. Порт виден только внутри общей сети Docker Compose, то есть другим контейнерам в том же compose-проекте. Поэтому порт 8008 недоступен с хост-машины, но доступен контейнеру HAProxy, который использует его для проверки состояния узлов через REST API Patroni.

Порт 5432 указан в `ports`, потому что это основной порт PostgreSQL, к которому должны подключаться клиенты с хоста. Порт 8008 указан в `expose`, потому что он нужен только HAProxy и узлам кластера для внутренней коммуникации. Это REST API Patroni, через которое можно сменить лидера, перезапустить узел или выполнить другие управляющие операции без аутентификации. Публикация этого порта на хосте создаёт угрозу безопасности, поэтому его лучше закрыть от внешнего доступа.

### 5.2. При обычном перезапуске композ-проекта, будет ли сбилден заново образ? А если предварительно отредактировать файлы postgresX.yml? А если содержимое самого Dockerfile? Почему?

Нет, в обоих случаях образ не будет пересобран. Образ, это набор настроек и файлов, который собирается один раз при выполнении `docker compose build` или `docker compose up --build`. После сборки образ сохраняется в локальном репозитории Docker с именем `localhost/postres:patroni` и не меняется автоматически при изменении исходных файлов.

При обычном перезапуске через `docker compose up -d` Docker запускает контейнеры из уже существующего образа. Если вы отредактируете файлы `postgres0.yml` или `postgres1.yml`, изменения не применятся, потому что эти файлы были скопированы в образ на этапе сборки через инструкцию `COPY` в Dockerfile. Контейнер использует файлы, которые уже находятся внутри образа, а не текущие версии на хосте.

Аналогично, если вы измените содержимое самого Dockerfile, это не приведёт к автоматической пересборке образа. Docker не отслеживает изменения в Dockerfile при обычном запуске compose-проекта.

Для пересборки образа не нужно менять файлы. Нужно явно вызвать команду `docker compose up -d --build`, которая принудительно пересоберёт образ перед запуском контейнеров. Только после этого изменения в `postgresX.yml` и `Dockerfile` будут учтены.

## 6 Заключение

В ходе лабораторной работы был успешно развернут высокодоступный кластер PostgreSQL. Протестированы ключевые механизмы HA:

- синхронная репликация данных между узлами;
- защита слейвов от операций записи;
- автоматический failover при отказе мастера: после кратковременной недоступности (порядка ttl = 30 с) HAProxy автоматически перенаправил клиентов на нового лидера;
- автоматическое восстановление и ресинхронизация вернувшегося в строй узла.

Все требования лабораторной работы выполнены, кластер функционирует в штатном режиме.
